GrepThink uses **two separate Supabase projects**: DEV (`jfbagjjvryqcwxsyeyeg`,
the only project that exists today) and a PROD project you create. These files
build a fresh PROD database from scratch; production never touches the dev DB.

| File | Purpose |
|------|---------|
| `schema.sql` | Public-schema DDL (tables/enums/functions/public triggers), generated by `npx supabase db dump`. |
| `auth_glue.sql` | Cross-schema bits a public dump misses: `auth.users` trigger, access-token-hook grants, RLS safety-net, security hardening, and the dashboard checklist. |
| `storage.sql` | Storage buckets (`class`/`profile`/`project`) + their policies (the storage schema isn't in a public dump). |

## RLS posture (important)

RLS is **enabled on every table, with no policies** — and for this app that is
**correct, not a gap**. All table access goes through the FastAPI backend using
the **service-role key** (which bypasses RLS); the browser only ever calls
Supabase **Auth** and **Storage**, never tables directly. RLS-on + no-policies
means the public anon key is default-denied on every table while the backend
still works. The advisor's `rls_enabled_no_policy` (INFO) notices are expected
here — **don't add table policies** unless you later let the browser query
tables directly. Keep RLS ON in prod (verify after building).

## Build order (fresh PROD)

```bash
# 1. capture the real public schema from DEV
npx supabase login
npx supabase link --project-ref jfbagjjvryqcwxsyeyeg
npx supabase db dump -f supabase/schema.sql --schema public

# 2. in PROD SQL Editor, run in order: schema.sql → auth_glue.sql → storage.sql
# 3. PROD dashboard steps (auth_glue.sql §5): Custom Access Token hook,
#    Auth Site URL/redirects, Google provider, leaked-password protection
# 4. create a prod instructor + student account (auth is per-project)
```

## Live inventory (verified 2026-06-18 via Supabase MCP — sanity-check the dump)

**22 tables:** `profiles`, `classes`, `class_enrollments`, `class_tas`,
`roster_entries`, `projects`, `project_members`, `project_join_requests`,
`project_ta_assignments`, `assignments`, `TSRs`, `feedback_submissions`,
`attendance`, `notifications`, `interest_form`, `interest_submissions`,
`interest_team_preferences`, `conversations`, `messages`, `conversation_reads`,
`conversation_deletes`, plus the `v_user_role` view.

**3 enums:** `request_status` (pending/approved/rejected), `term`
(fall/winter/spring/summer), `user_role` (student/teacher/ta/guest — legacy;
note `profiles.role` is a TEXT column CHECK'd to instructor/student instead).

**5 functions / 3 triggers:** `handle_new_user` (→ `on_auth_user_created` on
auth.users), `custom_access_token_hook` (Auth hook), `bump_conversation_last_message`
(→ messages), `profiles_role_sanitizer` (→ profiles), `handle_auth_sync`
(dead — references a non-existent `display_name` column). See `auth_glue.sql`
for the known inconsistencies before mirroring.

**Storage buckets:** `profile`, `project` (public) — recreate in prod.

> If a `db dump` is missing any table above, or you skip `auth_glue.sql`, a
> fresh prod will be subtly broken (most visibly: signups won't create profiles).

## Keeping dev → prod in sync

Fresh-build model, no auto-migrate: when the dev schema changes, re-run the
`db dump`, re-apply the changed DDL to prod, and update `auth_glue.sql` if any
trigger/function/Auth-hook/bucket changed.

## Institutions and class creation (maintainer steps)

In this order (the SQL files are in `backend/database/migrations/`):

1. `2026-09-25_institutions.sql`, then `2026-09-25_seed_istinye.sql`, DEV then PROD, before anyone
   creates a class outside UC Santa Cruz. Until the first file runs, no class can be given a school,
   and that file's one-time backfill labels every existing class UC Santa Cruz; a non-UCSC class
   created before both files have run would be mislabeled the same way, and re-running the backfill
   afterwards is not a fix (see the migration's own header). The backend works on either schema (the
   institutions loader in `app/institutions/controller.py` falls back to "no schools" while the
   table is missing), so both may be applied before or after the per-class-roles release.
2. `2026-09-25_messages_inbox_class_roles.sql` (the inbox's `can_send` now follows shared classes,
   not the account role), DEV then PROD. It is independent of the release and may be applied on
   either side of it, but it must run before the role flip in step 4: until it does, the inbox
   disables the composer of every DM between two instructor accounts, so once Scott is flipped,
   their thread with the UCSC instructor they TA for shows sending disabled, although the backend
   would allow the send.
3. Release beta → main.
4. Only once steps 1–3 are done on PROD: the role flip, `prod/2026-09-25_scott_class_creation.sql`
   (below).

- **Add a school:** copy `backend/database/migrations/2026-09-25_seed_istinye.sql`, change the name,
  slug (lower-case, hyphens) and base email domains, run it on DEV then PROD. The app shows it within
  about ten minutes: the backend caches the list for five minutes, and browsers keep it for another
  five (`Cache-Control: max-age=300`). An app tab that is already open keeps the list it loaded until
  it is reloaded. Subdomains of a listed domain count automatically — never list a public suffix
  (`edu.tr`, `ac.uk`, `com`, ...) in `email_domains`, since that would make every address under it
  a school email. (The loader also drops a small denylist of two-part public suffixes and any
  domain with no dot, logging an error (so Sentry reports it) rather than failing.)
- **Letting an existing account create classes:** edit and run
  `backend/database/migrations/prod/2026-09-25_scott_class_creation.sql` (it flips `student → instructor`
  for one email and refuses to change anything else). Run it only once steps 1–3 above are done on
  PROD. It takes effect within a minute; the user sees "Create Class" after reloading. Their classes
  as a TA or student are unaffected.
