# Project documents

Read this before changing `backend/app/documents`, its migration (`2026-11-17_project_documents.sql`), `frontend/src/lib/api/documents.ts` or `frontend/src/features/documents`.

- **One engine, a registry of kinds.** `app/documents/kinds.py` files each kind (sprint report, release summary, test plan and report) with its body model, its seed, its derived sections (`derive.py`, what the board says), its finalize checks and its Markdown (`markdown.py`). The database also allows `sprint_plan` and `release_plan`; the API answers 422 for them until they are filed there.
- **Save is last-writer-wins.** Every `PUT /api/documents/{id}` is a new revision, with no lock and no merge; `overwrote` names a revision someone saved after the one the edit started from (`base_revision`). A body or a snapshot over 200,000 bytes of compact UTF-8 JSON is refused ("This document is too long").
- **Finalize stamps the head and freezes the derived sections.** `document_finalize` refuses (409) unless the revision is still the head, stores the derived sections on it (`snapshot`, with `finalized_at` and `finalized_by`) and makes the document final. A later save leaves it final at its finalized revision (`edited_since`). Finalizing the finalized revision again writes nothing and answers NULL, so the API tells nobody twice.
- **Every hand-in is kept.** A revision that carries a snapshot answers it whichever hand-in is the document's latest, the revisions list marks each one (`finalized_at`), and pruning never deletes it; every other revision derives from the board now.
- **A sprint report describes the sprint as it ended.** Every burnup snapshot the board takes also records the sprint's stories in board order, each with whether it was completed, its tasks' hours and its points (`sprint_burnup_days.stories`), and the report reads the last saved day on or before the sprint's end that has one (`as_of`), else the board now (`as_of: "now"`). It lists the recorded stories that still exist (a deleted one counts nowhere), counts only the completed ones and the hours in them (the burnup still counts every done task), and shows what was finished after the end, among those still in the sprint, apart from its numbers (`after_sprint`, null without a record). A points edit takes no snapshot, so a record holds the points of the sprint's last snapshot.
- **Who:** the board's rule (`scrum.controller.board_access`): members read and write, staff read. Finalizing and deleting take `scrum master`, `product owner`, `owner` or `admin` (`project_members.role`). A class's list is its instructor's and TAs'. A class schedule never deletes a sprint that holds a document.
- **The SQL functions are the only writers of revisions:** `document_create` (no row lock: the unique indexes refuse a second document), `document_save` and `document_finalize` (each under the document's row lock), and `prune_document_revisions` (a daily pg_cron job, `prod/2026-11/`), which keeps only the head and the hand-ins once a sprint ended 7 days ago or a class's last day was 30 days ago.
- **Finalizing tells the meeting TA and the Review TA** (`notify.py`): an in-app notification and an outbox email deduped per revision and recipient. A failure there is logged with ids only and never fails the finalize.
- **The web client** (`frontend/src/features/documents/`). The board's Documents tab (`?view=documents`, `DocumentsTab`) lists the team's slots and starts a document. `/app/projects/:projectId/documents/:documentId` (lazy) is its page: `useDocument` holds the revision on screen, the body being edited and the writes. A member edits the head only, there is no autosave, and a save reads back the revision it stored, so the board's sections follow the body. One editor per kind sits beside the board's sections (`FromBoard`), `RevisionsDrawer` compares two revisions (`utils/diff.ts`), and `/app/documents/:documentId` opens a document by its id alone (the `document_finalized` notification). Keep two files in step with the backend: `utils/checks.ts` repeats `derive.py`'s blocking checks word for word, and `config/limits.ts` repeats `models.py`'s limits. The unsaved-changes guard (`useLeaveGuard`) wraps the router's navigator: the app's `BrowserRouter` is not a data router, so `useBlocker` is not available; a navigation it holds is made once the page turns clean. A write's answer that lands after the page moved to another revision changes nothing on screen, and loading the revision being edited again keeps unsaved typing. The story pickers read `GET /api/projects/{project_id}/documents/stories` once for the document's own project (`useProjectStories`), never the scrum board: that route lists every live story in board order with its sprint, criteria and completion, and writes nothing (no burnup snapshot, no event), while the board's own read does. Download Markdown and Copy give the latest hand-in, else the head; the page says so when that is not the revision on screen. On TA Meetings, staff see each team's "n of m handed in", from one `GET /api/classes/{class_id}/documents` for the page.
